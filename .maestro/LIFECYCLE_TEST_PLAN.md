## 1. Preconditions and fixture

One seeded set, recreated before each full run, so both roles can assert the same values:

- Owner account with one property `LC Fixture Flat` in status `available`, rent R12 500, with photos.
- Tenant account with a complete profile (ID number, email, phone, proof of address) and no active lease.
- Second tenant account with a complete profile, for competition and "property no longer available" checks.
- Vendor account approved for the property's area, for stage 7.
- A run token `${LC_TOKEN}` typed into every free-text field so each record can be found on the other side.
- A database reset script that deletes the viewing, application, holding deposit, lease, inspection, payment and maintenance rows created by the token and puts the property back to `available`.

Every action button needs a testID before these flows can be written reliably (332 of 375 have none). IDs are listed per screen in the inventory.

## 4. Element sweep

For each of the 37 screens in the inventory, one flow that opens the screen in each data state it has (empty, loaded, error where reachable) and taps every row in that screen's table, asserting the expected result for each: a navigation, a modal, an alert with the listed buttons, or a visible state change. A screen's sweep passes only when every row has been exercised. Conditional elements ("Shown when" column) need the fixture in the matching state.
